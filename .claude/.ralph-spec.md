## Goal
Build a visually engaging, easy-to-navigate **informational web portal** for WCTC's CTE programs. The homepage is a **literal hub-and-spoke** layout: a central multicolor "WCTC" logo (links to *About WCTC*) surrounded by 7 program nodes (each links to a dedicated program page), plus a docked **Administrative & Student Resources** panel. The site lets students, parents, and community members quickly learn about programs, staff, graduation requirements, and student opportunities. Built as a **React + Vite** SPA, run locally now, and structured for a clean handoff to **Firebase Hosting**.

## Constraints
- **Stack:** React + Vite (SPA), React Router for client-side routing.
- **Routing/hosting:** Static build (`dist/`) deployable to Firebase Hosting; SPA rewrites (`** → /index.html`).
- **Content (this build):** **Placeholder scaffold** — every page is structurally complete with realistic placeholder text, placeholder images, and explicit `TODO: replace` markers. No real teacher data/photos required yet.
- **Homepage layout:** Literal radial hub-and-spoke on desktop/tablet (≥900px). **Collapses to a vertical card grid + resources list under 900px** for mobile usability.
- **Logo:** Recreated in code as a swappable SVG/CSS wordmark (red/blue/yellow/green), isolated in a `<Logo>` component so an official `/assets/logo.svg` can replace it in one change.
- **Branding palette:** red, blue, yellow, green (Google-style multicolor) drawn from the logo; defined as CSS custom properties / theme tokens.
- **Content maintainability:** Page content lives in structured data files (`src/data/*.js|json`), not hard-coded in JSX, so non-developers can later edit content and it's a clean path toward a CMS.
- **Accessibility:** Semantic HTML, alt text on images, keyboard-navigable nodes/links, sufficient color contrast.

## Non-Goals
- No real/authentic teacher photos, names, course lists, or student work in this build (placeholders only).
- No backend, database, authentication, or login/portal accounts.
- No CMS integration in this build (data-file structure only, as a future on-ramp).
- No actual Firebase deployment in this build — config is prepared and committed, deploy happens at handoff.
- No pan/zoom canvas or radial-on-mobile; mobile uses the card-grid fallback.
- No Next.js / SSR / server functions.

# Part 2 — Authenticated In-Place Content Editing ("Edit Mode")

## Metadata
- **Phase:** 2 (builds on the Part 1 portal)
- **Type:** brownfield extension
- **Generated:** 2026-06-08
- **Status:** SPEC DRAFT (clarified, pending implementation)
- **Depends on:** Part 1 (portal must exist and deploy to Firebase Hosting)

> **⚠️ Supersedes Part 1 Non-Goals.** Part 2 intentionally reverses three Part 1
> Non-Goals: "No backend, database, or authentication," "No CMS integration," and
> "No login/portal accounts." Those constraints applied to the Part 1 placeholder
> build only. Part 1's static `src/data/*` files become the **seed** for the
> editable content store, not the runtime source of truth.

## Goal
Let authorized editors update the portal's **page content and images in place**,
through a login, without a developer or a redeploy. Each **program page** has its
own editor login that unlocks editing for that one page; a single **admin** login
can edit every page (all program pages plus About and all menu/resource pages).
Everyone else — the public — always sees a read-only **view version**. The site
stays a React + Vite SPA on Firebase Hosting; editing is powered by Firebase
services (Auth + Firestore + Storage).

## Roles & Authentication
| Role | Login (username) | Can edit | Cannot edit |
|------|------------------|----------|-------------|
| **Public visitor** | — (not logged in) | nothing — view version only | everything |
| **Program editor** | the program **slug** (e.g. `automotive`) | only *that* program's page | other programs, About, menu/resource pages |
| **Admin** | a single admin username | **every** page — all programs + About + all menu/resource pages | — |

- **Credential convention (per-program):** username = program slug; password set/rotated
  by the admin. Example: `automotive` / `wctcAutomotive2026`. The year in the example
  password signals **annual rotation**. There is **one shared credential per program**
  (shared among that program's teachers) — by design; the accountability trade-off
  (no per-person identity) is accepted for simplicity.
- **Firebase Auth is email/password-based**, so each username maps to a synthetic
  email behind the scenes (e.g. `automotive` → `automotive@edit.wctc.local`). The
  login form accepts the bare username and appends the fixed domain; users never see
  the email form.
- **Authorization is enforced by Firebase Security Rules (server-side), not the UI.**
  Each account carries custom claims (`role: "admin" | "program"`, `programSlug`).
  A program editor manipulating the client still cannot write another page's document,
  because Firestore/Storage Rules reject the write.
- **Account provisioning:** the 1 admin account and the per-program accounts are
  created by an admin-run setup (Firebase Admin SDK script or Firebase console),
  which also sets the custom claims. No public self-registration. Passwords are
  rotatable by re-running the script / console.

## What is editable (scope)
**Editable:** page **text content** and **images**. Not editable: site layout/structure,
routes/slugs, the hub-and-spoke geometry, the logo (still swapped in code per Part 1),
navigation chrome, or theme colors.

| Page | Editable text | Editable images |
|------|---------------|-----------------|
| Program page (×12) | tagline, overview, teacher name/title/email/phone/bio, course-sequence entries, certifications list, careers list, student-work titles/descriptions | program badge/hero image, teacher photo(s), student-work images |
| About | overview, mission, vision, contact info, resource-link labels | any About imagery |
| School Counselor / Leadership / Graduation / Program Sequences | section headings + body text | any in-page images |
| Home | intro/lede text, resources-panel labels | — (logo & node badges managed elsewhere) |

## Edit experience ("view version" vs "editable version")
- The **same pages** serve both versions — there is no separate public site.
- A **logged-out** visitor sees the normal page (view version); no edit affordances exist.
- A **logged-in** editor with rights to the current page sees an **"Edit" toggle**.
  Activating it turns the page's editable text into inline fields and shows
  replace-controls on editable images, **in place** on the real page.
- **Save** writes changes to Firestore (and uploads any new images to Storage);
  the change is then live for all visitors. **Cancel** discards unsaved edits.
- Saving is **immediate publish** (no draft/preview workflow in this phase).

## Rich-text content editing (decided)
Long-form body fields are edited with a **rich-text (WYSIWYG) editor**, not plain text.
- **Rich-text fields** (formatted): program overview, teacher bio, student-work
  descriptions, About overview/mission/vision, and the body text of each
  menu/resource page section, plus the Home intro/lede.
- **Plain-text fields** (no formatting): short single-line values — program name &
  tagline, teacher name/title/email/phone, course-sequence entries, certification
  and career list items, and section headings.
- **Allowed formatting:** a deliberately limited set — bold, italic, ordered/unordered
  lists, links, and headings (H2/H3). No arbitrary HTML, no embedded scripts/iframes,
  no inline styles.
- **Storage & safety:** rich text is stored as **sanitized HTML** (allow-list of the
  tags/attributes above). Content is **sanitized on save and again on render** so a
  compromised or mistaken value can never inject script (defense in depth). Editing is
  itself auth-gated, but sanitization is mandatory regardless.
- **Editor library:** recommend **TipTap (ProseMirror)** for React — headless,
  allow-list-friendly, small footprint; any equivalent that supports a restricted
  schema is acceptable.

## Data model & storage (Firebase)
- **Auth:** Firebase Authentication, email/password provider (username-mapped).
- **Content:** Cloud Firestore.
  - `programs/{slug}` — one document per program holding all editable fields.
  - `pages/{pageId}` — one document per non-program page (`about`, `counselor`,
    `leadership`, `graduation`, `program-sequences`, `home`).
  - **Seed once** from the existing `src/data/programs.js` / `resources.js` / `site.js`
    so day-one content matches the current site; thereafter Firestore is the source
    of truth and the app reads from it (static files remain as the seed + offline fallback).
- **Images:** Firebase Storage, public-read; uploaded files replace the referenced
  URL in the corresponding Firestore document.
- **Security Rules (server-enforced):**
  - Read: public (anyone) for `programs/*`, `pages/*`, and Storage images.
  - Write `programs/{slug}`: allowed if `request.auth.token.role == "admin"`, or
    (`role == "program"` **and** `request.auth.token.programSlug == slug`).
  - Write `pages/*`: allowed only if `role == "admin"`.
  - Storage writes: same role checks, keyed by path (e.g. `programs/{slug}/...`).
- **Firebase web config (apiKey, etc.) is public by design** — security lives in
  Rules and custom claims, never in the client bundle.
